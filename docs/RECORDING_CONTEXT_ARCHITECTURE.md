# 录播结构化上下文与兴趣点发现架构

状态：设计方案，未实现本文新增的弹幕关联、事件关系与兴趣点对象。现有实现见 `CHAT_CLIPPING.md` 和 `src/core/chat-clip.ts`。本文不表示已有可靠声纹身份识别或已完成样片弹幕匹配。

## 1. 当前实际流程

1. 输入录播，Qwen ASR 生成带时间的字词。
2. 终末地/B站词库校核。
3. 本地音色聚类，为字词附匿名声音簇；簇按五分钟窗口作用，不是全场人物身份。
4. Terra high 分批读取前后文，校核断句，给出 `host/game/uncertain`、topic 和疑点。
5. Terra high 从话语序列直接选择完整聊天片段；长稿分批提出候选再排序。
6. 入选疑难句带音频上下文重新识别、Terra 再校核；实质改字重新对齐。
7. 根据字词间隙确定首尾余量，导出无句读标点字幕、视频与上下文对照表。
8. 可选 Sol high 原片/成片抽帧对照，输出画面检查记录。

当前没有独立的、带触发事件与铺垫/回应关系的兴趣点对象。聊天管线尚未读取弹幕原文并关联回应；仓库已有的弹幕解析/热度模块可复用，但不等于它已经接入聊天管线。画面检查目前主要在导出后，不负责构建剧情对白时间线。

## 2. 核心数据模型：多条并行时间线

不能把整段时间简单归类为“游戏”或“聊天”。游戏剧情、主播与弹幕互动可能同时发生。

分开记录：

- **画面状态**：剧情、战斗、菜单、加载、未知。
- **声音来源**：主播麦克风、游戏音频、连麦、混合、未知。
- **实际说话者**：主播、角色A、角色B、连麦者、未知；有证据才归名。
- **话语行为**：读弹幕、回应观众、游戏对白、朗读游戏文本、点评游戏、闲聊、感谢礼物。
- **话语指向**：某条弹幕、另一个角色、上一句话、观众整体、未知。

例如主播朗读角色台词：实际说话者仍为主播，行为是朗读游戏文本，被引用角色另记。不要因为内容像台词就把声源改成游戏。主播转回游戏点评：实际说话者不变，话题和行为发生变化。

推荐分为以下五层。

### 2.1 会话背景 SessionContext

保存主播已知身份、昵称、房间、游戏、直播主题、游戏版本/章节、人物及别名词表。每条背景注明来自用户、录播元数据还是核验过的资料；未知留空。不要用游戏百科的完整剧情替代视频证据，也不要凭声音猜真实人物身份。

背景按会话保存，游戏切换、章节变更等做增量更新。人物表使用 ID，名称与别名只在字典中定义一次。

### 2.2 原始证据 Evidence

- ASR 原稿、校核稿、字词时间、对齐来源。
- 麦克风/桌面音频轨信息。录制条件允许时分别保留两轨；既有混音只能尽力归属，不能保证拆开叠音。
- 匿名声音簇及其作用窗口。
- 原始弹幕、SC、礼物事件的内容和时间；发送者在分析层使用匿名 ID。
- 按需抽取的画面、角色名、屏幕字幕及 OCR 置信度。

所有证据保留文件标识、原始时间、归一化时间和来源引用。LLM 的结论不能覆盖原始记录。

### 2.3 标准事件 TimelineEvent

```json
{
  "id": "u_042",
  "interval": [170.0, 174.0],
  "kind": "utterance",
  "audio_origin": "unknown",
  "speaker_id": "host_01",
  "speaker_cluster": "window_0:cluster_20",
  "speaker_basis": ["voice_cluster", "addressing_viewers"],
  "activity": "reply_to_chat",
  "quoted_speaker_id": null,
  "text_raw": "转写原文",
  "text_reviewed": "校核后的话语",
  "topic_id": "topic_voice_request",
  "reply_to": [{"event_id": "d_017", "status": "candidate"}],
  "evidence_refs": ["asr:w510-w530"],
  "confidence": {
    "speaker": "medium",
    "reply_link": "low",
    "text": "high"
  }
}
```

这是结构示意，不是已核验的样片记录。置信等级是待校准的判断，不伪装成统计概率。声音来源可以未知，但语境支持说话者可能是主播；二者不能混为一个字段。并发/重叠事件保留各自时间区间，不强行排成互斥句段。

### 2.4 互动与话题 Episode

将事件关联为可解释的对话链：

`观众提问 → 主播读出 → 主播回答/解释 → 观众或主播反应 → 收束`

也允许：

`游戏角色对白 → 主播吐槽 → 弹幕接梗 → 主播回应`

每个 episode 保存参与者、涉及事件、主题、当前阶段、未回答的问题、必要前文、结束证据，以及同时发生但无关的游戏事件。

话题状态可为 `open / responding / resolved / suspended`。打游戏导致短暂打断时先挂起，后续回来继续答可关联同一话题；换画面不等于话题结束。选择切片时仍优先连续、能独立理解的范围，跨很长中断的拼接另作显式编辑决策。

### 2.5 兴趣点 InterestCandidate

```json
{
  "id": "interest_007",
  "episode_id": "topic_voice_request",
  "kind": "unexpected_reply",
  "why_interesting": "观众请求角色声音，主播解释约定并用本声回应",
  "trigger_events": ["d_017"],
  "setup_events": ["u_038"],
  "payoff_events": ["u_042", "u_053"],
  "resolution_event": "u_054",
  "required_context": ["u_038", "u_041"],
  "exclude_after": "u_055",
  "exclude_reason": "主播开始回顾错过的游戏剧情",
  "evidence_refs": ["episode:topic_voice_request"],
  "interest_level": "high",
  "evidence_confidence": "medium",
  "completeness": "resolved",
  "review_needed": ["confirm_chat_reply_link"]
}
```

同样为示意。候选先引用事件，最终切点由真实字词、停顿与音频证据推导；不得把模型估计的整数秒直接当精准切点。

## 3. 时间对齐和弹幕关联

1. 用视频 PTS/音频时间建立统一媒体时钟；保留绝对录制时间及原始偏移。
2. 多个五分钟文件属于同一会话时，建立分片清单与时间映射，记录断流、重连、重叠和缺口，不能简单把文件时长累加当作连续直播。
3. 检查弹幕是媒体相对时间、服务端时间还是本机接收时间。记录各轨 offset；长录播必要时校正时钟漂移。
4. 弹幕发出、主播收到、读出、观众反应存在不同延迟。先从主播明显读出的文字建立匹配锚点，再估计本场的偏移与响应延迟范围。
5. 为每句回应检索时间窗口内的候选弹幕，结合原文相似度、昵称/称呼、话题、问答关系排序。不能把最近的一条弹幕硬绑定为提问。
6. 一句可能回应多条弹幕，一条弹幕也可能引出多轮对话；无法确定时保留候选或空关联。
7. 主播读出的弹幕和弹幕原文关联为同一触发事件的两个观测，避免重复计分。热度做刷屏去重和相对基线归一化。

## 4. 兴趣点怎样产生

候选召回走多路，不先按热度过滤整场：

| 路径 | 触发信号 | 仍需核对 |
|---|---|---|
| 问答互动 | 问题、请求、主播明确回应 | 是否回答完整、回应哪条弹幕 |
| 反差/笑点 | 铺垫与意外回应、改口、自嘲、接梗 | 是否能指出实际转折句 |
| 完整话题 | 观点、经历、解释与结论 | 脱离直播上下文能否理解 |
| 游戏引发互动 | 游戏事件后主播评论、弹幕回应 | 游戏事件是否是笑点必需前文 |
| 观众反应 | 弹幕突增、重复梗、笑声、SC事件 | 热度针对游戏剧情还是主播互动 |

礼物金额、音量大或弹幕多只提供候选线索，不自动等于有趣。安静但内容完整的聊天也进入候选。无素材不凑数量。

Terra high 对每个候选输出：有趣在哪里、关键原句、触发/铺垫/回应/收束证据、需要补的前文、应排除的下一话题。排序分开考虑内容吸引力、互动性、独立可懂程度、完整性和证据可靠性；阈值及权重需用人工偏好样本校准，不预设未经验证的准确率。

## 5. LLM 的读取方式与职责

每次输入只组装一个 ContextPacket：

1. 会话背景与人物/词汇字典的必要部分。
2. 当前游戏状态、正在继续的话题、未解决的问题。
3. 当前窗口的事件表（ID、时间、说话者、行为、文本、关联）。
4. 与这些事件有关的弹幕原文、代表性反应及聚合热度。
5. 必要前后文与待消歧事项；仅当画面能解决疑点时附少量带时间图像。

完整证据在本机；LLM 用 ID 按需检索原句和画面。背景与角色字典不在每句重复。普通弹幕先去重/聚合，但被回复的具体弹幕必须保留原文。滚动摘要必须保留事件引用，后续决策不能只依赖摘要而失去关键原句。

- Qwen：ASR 与时间对齐。
- Terra high：文字校核、行为/话题结构、弹幕关联、兴趣点召回与复核。角色或话题关键字的疑点先补证，再选择候选；普通字幕疑点在候选阶段精校。
- Sol high：按需识别画面状态、屏幕角色名/字幕、消解具体视觉疑点，以及导出后的画面对照。不能从画面推断未听到的对白。
- 确定性程序：时间对齐、ID/范围校验、去重、证据存取、边界裁切、字幕排版和导出。

这是逻辑阶段，不要求每阶段都是常驻独立 agent，避免无必要的重复模型调用。

## 6. 切片策略的必要变化

现有聊天选择会拒绝包含 `game` 话语的候选。新架构应改成判断游戏事件是否为当前兴趣点的必要前文：

- 无关的剧情对白、话题结束后的游戏解说：排除。
- 主播吐槽所针对的那句角色台词：可以保留最小必要范围。
- 游戏和聊天同时发生：保留视频中的原始并发关系；字幕以配置的主体为主，叠音不确定则提示。

音色边界、画面切换、ASR 窗口边界都不能单独作为话题边界。先确定必要事件与收束，再用字词/停顿检查首尾。真实气口不足要显式记录；不能带入下一话题伪装成气口。

## 7. 落地顺序与验收

第一步：统一媒体/弹幕时钟，接入现有 XML/JSONL 解析，建立 SessionContext 和多轨事件表。

第二步：给 `ReviewedTurn` 增加来源、行为、指向和独立的置信字段；建立主播读弹幕与原始弹幕的候选关联。

第三步：建立 episode 与结构化兴趣点对象，替换直接从话语列表选首尾的流程；保留既有校核、对齐、导出和上下文对照表。

第四步：按需接入游戏画面状态、角色名/对白 OCR，支持“游戏触发—主播反应”的混合兴趣点。

用带人工标注的小样本验证：

- 剧情播放同时主播回答弹幕，不误切到剧情。
- 主播回答结束转回游戏，不因声音相同而延长话题。
- 主播读游戏台词，实际说话者不误标成游戏音轨。
- 游戏台词是包袱前文时保留，独立剧情不混入。
- 弹幕延迟、没有弹幕、叠音和未知角色时保留不确定性。
- 跨录制分片的话题不丢失铺垫，不把重叠文件的内容重复计数。

记录角色归属准确率、弹幕关联准确率、完整话题召回、切点截声率、候选人工采用率，以及每小时录播的模型用量。指标需要标注后测量，本方案不预报数值。
